## Overview

Spec 1 ของ admin-identity roadmap (plan: `~/.claude/plans/sprightly-painting-token.md`). สองงานในก้อนเดียว:
(ก) เปลี่ยนชื่อ producer-side actor `TenantUser*` -> `ProducerAccount*` ทั้ง stack แบบ behavior-preserving;
(ข) สร้างฐาน admin identity ครั้งแรก (Super/Scoped tier, admin<->tenant M:N, bootstrap, accessible-tenant
resolution, app-layer scoped floor) บน pol-core (modular monolith, EF Core 10 + SQL Server 2025 RLS). ผูกกับ
product canon: control plane (admin) แยกขาดจาก data plane (producer) ตั้งแต่ token ยันตาราง. **Out of scope
(ไป Spec 2/3):** enum->permission catalog, delegation/grant-time intersection, `orders.created_by`.

## REQ-1: Producer actor rename (behavior-preserving)
**User Story:** As the platform maintainer, I want `TenantUser*` renamed to `ProducerAccount*` across the whole
stack, so that code matches the domain language without changing any behavior.
**Source:** design §"C# + EF rename map", §"Renamed tables / columns".
**Acceptance Criteria (EARS):**
- 1.1 THE SYSTEM SHALL preserve the existing producer-side SEMANTIC behavior after the rename; renamed identifiers (route, claim, types, tables) and the tests asserting them change in lockstep — semantics, not strings, are what is preserved. (analyze F1A)
- 1.2 THE SYSTEM SHALL rename DB objects `TenantUsers`->`ProducerAccounts`, `TenantUserProfiles`->`ProducerAccountProfiles`, columns `TenantUserId`->`ProducerAccountId`, and their PK/index names, preserving existing row data.
- 1.3 THE SYSTEM SHALL preserve the `ProducerAccount.Role` column as `int` with values `Viewer/Finance/TenantAdmin` unchanged (no role data migration).
- 1.4 THE SYSTEM SHALL update every non-compiler-verified reference (EF `ToTable`/`Property` string literals in `IdentityConfigurations.cs`, the model snapshot, and test SQL/helpers `IntegrationDb`) so the rename commit builds and all tests pass.
- 1.5 IF the migration is generated by EF auto-scaffold (emitting DROP+CREATE) THEN THE SYSTEM SHALL reject that approach in favor of a manual-authored rename that preserves data.

## REQ-2: External contract rename (actor / claim / route)
**User Story:** As an Admin SPA integrator, I want the external rename limited to the actor-facing surface, so
that the approve route and producer role claim read coherently without churning the SPA audience plumbing.
**Source:** design §"External HTTP contract changes".
**Acceptance Criteria (EARS):**
- 2.1 THE SYSTEM SHALL rename the approve route `/admin/tenant-users/{subject}/approve` -> `/admin/producer-accounts/{subject}/approve` and the `tenant_role` claim -> `producer_role`.
- 2.2 THE SYSTEM SHALL keep the approve request JSON field shape `{TenantId, Role}` unchanged (only the C# record type name changes), so the Admin SPA changes only the route URL.
- 2.3 THE SYSTEM SHALL retain the SPA audience-role key `tenant` unchanged (DESCOPED per analyze F8B): the rename is limited to actor/table/claim/route; the audience policy label, env var `Google__Audiences__tenant`, the middleware role literal, and all 13 `RequireAuthorization("tenant")` call sites stay `tenant`.
- 2.4 THE SYSTEM SHALL NOT require any tenant-SPA change (audience key + OAuth client id unchanged).

## REQ-3: Admin account model
**User Story:** As the platform, I want admins persisted as first-class accounts with a tier, so that admin
identity and privilege level are explicit and queryable.
**Source:** design §"Data Models — AdminAccounts", §"New interfaces — AdminAccount".
**Acceptance Criteria (EARS):**
- 3.1 THE SYSTEM SHALL store admin accounts in `AdminAccounts` with `Email`, `Tier` (Super/Scoped), `Status` (Active/Suspended), and a `Subject` (Google sub) that is unique once bound; an invited-but-not-yet-logged-in Scoped account has an unbound `Subject` and is keyed by its unique verified `Email` until bound. (analyze F4A)
- 3.2 THE SYSTEM SHALL place `AdminAccounts`, `AdminTenantAssignments`, and `AdminAccountAudits` as control-plane tables: granted to `pol_admin` only, with NO per-tenant RLS predicate and NO grant to `pol_app`.
- 3.3 THE SYSTEM SHALL NOT assign admin accounts a `PendingApproval` status (admins are bootstrapped or created by a Super, never self-approved through the producer flow).
- 3.4 WHEN a Super Admin creates a Scoped Admin THE SYSTEM SHALL provision an `AdminAccount` (Tier=Scoped) by verified email with an unbound `Subject` and write a `create-scoped` audit (mirrors the producer RegistrationTicket invite pattern). (analyze F4A)
- 3.5 WHEN an admin-audience caller's Google `sub` is unbound AND their verified email matches a pending invited Scoped account THEN THE SYSTEM SHALL bind the `sub` to that account on first login and resolve it. (analyze F4A)

## REQ-4: Admin-tenant assignment (M:N)
**User Story:** As a Super Admin, I want to assign and unassign tenants to a Scoped Admin, so that a Scoped
Admin's reach is exactly the tenants delegated to them.
**Source:** design §"Data Models — AdminTenantAssignments", seq "Super creates Scoped admin + assigns tenant".
**Acceptance Criteria (EARS):**
- 4.1 WHEN a Super Admin assigns a tenant to a Scoped Admin THE SYSTEM SHALL create one `AdminTenantAssignment` row, enforcing uniqueness on `(AdminAccountId, TenantId)`.
- 4.2 WHEN a Super Admin unassigns a tenant THE SYSTEM SHALL hard-delete the assignment row (the migration grants `DELETE` on `AdminTenantAssignments` to `pol_admin`).
- 4.3 IF an assignment targets a tenant that is unknown or not Active THEN THE SYSTEM SHALL respond 409 (reusing `ITenantDirectory.IsActiveTenantAsync`) and create nothing.
- 4.4 IF an assignment duplicates an existing `(AdminAccountId, TenantId)` THEN THE SYSTEM SHALL respond 409.

## REQ-5: Super Admin bootstrap (allowlist self-provision, idempotent)
**User Story:** As the platform operator, I want the first Super Admin to bootstrap from a config allowlist on
first login, so that there is no chicken-and-egg approver problem.
**Source:** design seq "idempotent bootstrap self-provision", §"Technology Decisions — Bootstrap".
**Acceptance Criteria (EARS):**
- 5.1 WHEN an admin-audience caller whose Google `sub` is in `AdminAllowlist:Subjects` first authenticates and has no `AdminAccount` THEN THE SYSTEM SHALL self-provision them as `Super`/`Active` and write a `self-provision` audit.
- 5.2 IF two first-logins for the same subject race THEN THE SYSTEM SHALL catch the unique-violation (2601/2627), re-read the existing account, and proceed (exactly one row; both requests resolve).
- 5.3 IF an admin-audience caller's subject is NOT in the allowlist and has no `AdminAccount` THEN THE SYSTEM SHALL deny with 403 and self-provision nothing.
- 5.4 IF `AdminAllowlist:Subjects` is empty/unset outside Development THEN THE SYSTEM SHALL emit a boot-time warning / not-ready health signal AND deny first-admin login (fail-closed, never auto-Super).
- 5.5 THE SYSTEM SHALL source allowlist subjects from environment configuration only (never committed).
- 5.6 IF a resolved `AdminAccount` has `Status = Suspended` THEN THE SYSTEM SHALL deny with 403 and bind nothing (mirrors a suspended producer resolving to null). (analyze F5A)
- 5.7 THE SYSTEM SHALL treat `AdminAllowlist:Subjects` as a bootstrap gate checked ONLY at self-provision; removing a subject SHALL NOT revoke an existing `AdminAccount` — revocation is via `Suspend`. (analyze F7A)

## REQ-6: Accessible-tenant resolution
**User Story:** As the authorization layer, I want each admin's accessible-tenant set resolved once per
request, so that scoped checks are cheap and consistent.
**Source:** design §"New interfaces — IAdminDirectory/AccessibleTenants", §"Technology Decisions — Resolution".
**Acceptance Criteria (EARS):**
- 6.1 THE SYSTEM SHALL resolve a Super Admin's accessible tenants as unrestricted (all tenants).
- 6.2 THE SYSTEM SHALL resolve a Scoped Admin's accessible tenants as exactly their `AdminTenantAssignments` set.
- 6.3 WHEN an admin request is authenticated THE SYSTEM SHALL resolve and materialize the accessible-tenant set once per request into `IAdminScope` (no per-query re-resolution) and add an `admin_tier` claim.

## REQ-7: Scoped-admin app-layer floor
**User Story:** As a security reviewer, I want scoped-admin tenant isolation enforced by a mechanism strong
enough to replace the RLS floor, so that a forgotten filter cannot leak cross-tenant data.
**Source:** design §"Scoped-admin app-layer floor".
**Acceptance Criteria (EARS):**
- 7.1 THE SYSTEM SHALL route every admin cross-tenant read through the single `IAdminQuery` seam, which applies `WHERE TenantId ∈ accessible` for Scoped admins and no filter for Super admins. The Spec-1 seam surface is the admin reads that actually exist (tenant read by code); speculative reads (e.g. cross-tenant reconciliation) are NOT added in Spec 1. (analyze F6A)
- 7.2 THE SYSTEM SHALL fail an Architecture.Tests rule (CI-failing) if an admin handler reads a tenant-scoped BUSINESS table cross-tenant without going through `IAdminQuery`. Control-plane provisioning repositories (Super-only writes via dedicated Tenant/PspConnection/Vault repos) are EXEMPT; the rule targets cross-tenant business-table reads, not all admin DB access. (analyze F2A)
- 7.3 WHEN a Scoped Admin queries data for a tenant not in their accessible set THE SYSTEM SHALL return nothing / deny (fail-closed).
- 7.4 THE SYSTEM SHALL record (in canon) that scoped-admin isolation is an app-layer exception to the RLS floor, with the seam + Architecture.Tests + leak/bypass tests as compensating controls.

## REQ-8: Admin authorization
**User Story:** As a Super Admin, I want privileged admin actions gated to Super and protected from
self-tampering, so that Scoped admins cannot escalate or lock out oversight.
**Source:** design §"Error Handling", §"New interfaces — AdminAccount.Suspend".
**Acceptance Criteria (EARS):**
- 8.1 IF a Scoped Admin invokes a Super-only action (create admin, assign/unassign tenant) THEN THE SYSTEM SHALL respond 403 (`RequireAdminTier(Super)`).
- 8.2 IF an admin attempts to suspend their own account THEN THE SYSTEM SHALL reject it (`AdminAccount.Suspend` throws when acting admin == target).
- 8.3 THE SYSTEM SHALL keep producer-side role authoring and delegation out of scope (deferred to Spec 2).
- 8.4 THE SYSTEM SHALL gate tenant provisioning (`POST /admin/tenants`) to Super only — a newly created tenant cannot be scoped to anyone. (analyze F3A)
- 8.5 WHEN a Scoped Admin reads a tenant (`GET /admin/tenants/{code}`) or approves a producer THE SYSTEM SHALL allow it only for tenants in their accessible set (filtered per REQ-7); a Super Admin is unrestricted. (analyze F3A)

## REQ-9: MFA assertion (Workspace-enforced, app best-effort)
**User Story:** As the platform, I want MFA enforced at the identity provider with a best-effort app-side
signal, so that we rely on Workspace policy without coupling to a claim Google may not send.
**Source:** design §"Technology Decisions — MFA", decision-3.
**Acceptance Criteria (EARS):**
- 9.1 WHERE an admin token carries an `amr`/`acr` MFA claim THE SYSTEM SHALL assert it and proceed.
- 9.2 IF an admin token carries no `amr`/`acr` claim THEN THE SYSTEM SHALL log its absence and admit the request (no hard gate; Workspace org policy is the enforcing control).
- 9.3 THE SYSTEM SHALL NOT treat the app-side `amr`/`acr` assertion as a contract with Google (tested with synthetic claims only).

## REQ-10: Admin audit (append-only, actor tuple)
**User Story:** As a compliance auditor, I want every admin identity/assignment change recorded immutably with
a typed actor, so that cross-tenant admin actions are traceable.
**Source:** design §"Data Models — AdminAccountAudits", §"Audit bridge".
**Acceptance Criteria (EARS):**
- 10.1 WHEN an admin performs self-provision, create-scoped, assign-tenant, unassign-tenant, or suspend THE SYSTEM SHALL append an `AdminAccountAudit` row with `(ActorType='admin', ActorId=acting AdminAccount.Id)` and a correlation id.
- 10.2 THE SYSTEM SHALL treat `AdminAccountAudits` as append-only (insert only; no update/delete).
- 10.3 THE SYSTEM SHALL NOT rewrite the existing `RegistrationAudits`/`ProvisioningAudits`/`VaultRevealAudits` to the tuple form (forward-only, decision-4); `AdminAccounts.Subject` is the bridge key to legacy `AdminSubject` strings.

## REQ-11: Migration safety
**User Story:** As the operator, I want the rename+add migration to be safe and reversible on the existing
RLS-policied schema, so that data is preserved and rollback is possible.
**Source:** design §"Migration mechanics".
**Acceptance Criteria (EARS):**
- 11.1 THE SYSTEM SHALL drop the `TenantUsers` FILTER/BLOCK predicates from `TenantIsolationPolicy` before renaming the table and re-add equivalent predicates on `ProducerAccounts` after.
- 11.2 THE SYSTEM SHALL leave `fn_tenant_predicate` unchanged (it is SCHEMABINDING to the `TenantId` column + SESSION_CONTEXT, not the table name).
- 11.3 THE SYSTEM SHALL provide a reversible `Down` migration (drop admin tables; restore predicates/grants/names to the pre-rename state).
- 11.4 WHEN the migration is applied and rolled back on a real SQL Server THE SYSTEM SHALL leave the security policy and predicates consistent with no data loss.

## REQ-12: Canon reconciliation
**User Story:** As a future spec author, I want the canon to match reality, so that downstream specs do not
cite a stale 2-schema/AdminUser model.
**Source:** design §"Non-Functional Considerations", plan "Canon / doc reconciliation".
**Acceptance Criteria (EARS):**
- 12.1 THE SYSTEM SHALL correct `ARCHITECTURE.md` and `CODING_STANDARDS.md` to describe the single `producer` schema and the `ProducerAccounts`/`AdminAccounts` actor model (removing the stale `admin`-schema/`AdminUser` references).
- 12.2 THE SYSTEM SHALL document the scoped-admin app-layer-floor exception in canon (per REQ-7.4).

## REQ-13: Admin SPA identity bootstrap (`GET /admin/me`)
**User Story:** As an Admin SPA, I want to read the calling admin's own identity, tier, and accessible
tenants after Google login, so that the SPA can render the right navigation/scope without guessing from the
opaque Google token.
**Source:** PR `feat/admin-identity-rbac` SPA-glue decision (not in original design; additive).
**Acceptance Criteria (EARS):**
- 13.1 WHEN an admin-audience caller is resolved (bound `IAdminScope`) AND requests `GET /admin/me` THE SYSTEM SHALL return `{ adminId, email, tier, accessibleTenants }`.
- 13.2 WHERE the resolved admin is `Super` THE SYSTEM SHALL return `accessibleTenants` as `{ isUnrestricted: true }` and SHALL NOT enumerate every tenant.
- 13.3 WHERE the resolved admin is `Scoped` THE SYSTEM SHALL return `accessibleTenants` as `{ isUnrestricted: false, tenants: [{ id, code }] }` containing exactly that admin's own assignments (never another admin's).
- 13.4 IF the caller's admin is not resolvable (not in allowlist, no invite) or `Suspended` THEN THE SYSTEM SHALL deny per REQ-5.3/5.6 before reaching the endpoint (the admin resolution middleware short-circuits).

## Edge Cases & Open Questions

- **Google `amr`/`acr` reality** — REQ-9 likely a no-op if Google ID tokens omit the claim. Verify via real token inspection during impl; if always absent, 9.1 exercised by synthetic tests only (accepted).
- **Self-provision in middleware** — REQ-5 writes during the resolution middleware pass (a write path the producer middleware lacks); accepted as idempotent (REQ-5.2). Revisit only if a read-only resolution is later required.
