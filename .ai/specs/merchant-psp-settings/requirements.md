# ข้อกำหนด: การตั้งค่าผู้ให้บริการรับชำระเงินของร้านค้า

> Status: approved 2026-09-06
> Status-Note: amended 2026-09-06

## ภาพรวม

Admin Console ต้องให้ทีมกลางตั้งค่าการเชื่อมต่อ 2C2P และ Omise/Opn แยกตามร้านค้า เปิดใช้ผู้ให้บริการ
แยกตามช่องทางชำระเงิน และกำหนดเส้นทางหลัก/สำรอง โดยรักษารูปแบบ redirect-only, PCI SAQ A,
การแยกข้อมูลร้านค้า และการเก็บรักษาข้อมูลลับในคลังข้อมูลลับ (vault) ตามสถาปัตยกรรมเดิม
ขอบเขตนี้ออกแบบหน้าตั้งค่าและสัญญาควบคุม ส่วนการเพิ่มกระบวนการชำระเงินจริงของ Omise PromptPay
และ installment เป็นข้อกำหนดแยกที่ต้องผ่าน sandbox ก่อนเปิดความสามารถ

คำสำคัญ `THE SYSTEM SHALL`, `WHEN`, `WHILE`, `WHERE`, `IF` และ `THEN` คงภาษาอังกฤษตามไวยากรณ์ EARS
ที่ระบบตรวจข้อกำหนดของรีโพซิทอรีบังคับใช้

## REQ-1: ขอบเขตของ Admin Console

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการจัดการการตั้งค่าผู้ให้บริการรับชำระเงินจากหน้าร้านค้าเดียว เพื่อให้ตั้งค่าการรับชำระได้โดยไม่ต้องสลับหลายหน้าหรือเปิดสิทธิ์ให้ผู้ใช้ร้านค้า

**เกณฑ์การยอมรับ (EARS):**

- 1.1 THE SYSTEM SHALL จำกัดหน้าตั้งค่าผู้ให้บริการรับชำระเงินของร้านค้าให้เฉพาะผู้ดูแลระบบส่วนกลางที่ยืนยันตัวตนแล้ว
- 1.2 THE SYSTEM SHALL NOT เปิดหน้าตั้งค่าหรือการแก้ไขค่าผู้ให้บริการรับชำระเงินใน Merchant Console
- 1.3 WHEN ผู้ดูแลระบบเลือกร้านค้า THE SYSTEM SHALL แสดงสภาพแวดล้อมการชำระเงิน การเชื่อมต่อ ช่องทางชำระเงิน เส้นทาง และคำขออนุมัติที่ค้างอยู่ของร้านค้านั้น
- 1.4 IF ผู้ดูแลระบบไม่มีสิทธิ์เข้าถึงร้านค้าที่ระบุ THEN THE SYSTEM SHALL ตอบ 404 โดยไม่เปิดเผยว่าร้านค้านั้นมีอยู่หรือไม่
- 1.5 THE SYSTEM SHALL ควบคุมการอ่าน การทดสอบ การขอเปลี่ยนข้อมูลรับรอง และการจัดการ routing ด้วย `settings.manage`
- 1.6 THE SYSTEM SHALL ควบคุมการสร้างหรือแก้การเชื่อมต่อด้วย `settings.manage` และ `merchant.manage`
- 1.7 THE SYSTEM SHALL ควบคุมการอ่านช่องทางระดับบัญชีผู้ให้บริการด้วย `merchant.view`
- 1.8 THE SYSTEM SHALL ควบคุมการแก้ช่องทางระดับบัญชีผู้ให้บริการด้วย `merchant.manage`

## REQ-2: สภาพแวดล้อมการชำระเงินของร้านค้า

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการเลือก sandbox หรือ live แยกต่อร้านค้า เพื่อให้แต่ละร้านค้าทดสอบและเปิดใช้จริงตามกำหนดของตน

**เกณฑ์การยอมรับ (EARS):**

- 2.1 THE SYSTEM SHALL เก็บ `Merchant.PaymentEnvironment` เป็นแหล่งข้อมูลจริงเดียว โดยรับค่า `sandbox` หรือ `live`
- 2.2 THE SYSTEM SHALL ให้การเชื่อมต่อทุกตัวสืบทอดสภาพแวดล้อมการชำระเงินจากร้านค้าโดยไม่เก็บค่าซ้ำบนการเชื่อมต่อ
- 2.3 THE SYSTEM SHALL อนุญาตให้ร้านค้าแต่ละรายใช้สภาพแวดล้อมการชำระเงินต่างกันในระบบที่กำลังทำงานชุดเดียวกัน
- 2.4 WHEN เรียกผู้ให้บริการรับชำระเงิน THE SYSTEM SHALL เลือก endpoint และรุ่นข้อมูลรับรองจากค่าที่ตรึงไว้กับรายการชำระเงิน
- 2.5 IF สภาพแวดล้อมของข้อมูลรับรองไม่ตรงกับสภาพแวดล้อมการชำระเงินของร้านค้า THEN THE SYSTEM SHALL ปฏิเสธก่อนเรียกผู้ให้บริการรับชำระเงิน
- 2.6 IF ผู้ดูแลระบบส่งค่าสภาพแวดล้อมการชำระเงินที่ไม่รู้จัก THEN THE SYSTEM SHALL ตอบ 400 โดยไม่บันทึกข้อมูล
- 2.7 WHEN สภาพแวดล้อมการชำระเงินที่ใช้งานอยู่เปลี่ยน THE SYSTEM SHALL ใช้สภาพแวดล้อมใหม่เฉพาะรายการชำระเงินที่สร้างหลังการเปิดใช้
- 2.8 WHILE รายการชำระเงินมีรายการภายนอกแล้ว THE SYSTEM SHALL ใช้การเชื่อมต่อ รุ่นข้อมูลรับรอง และสภาพแวดล้อมที่ตรึงไว้กับรายการนั้น
- 2.9 WHEN สร้างรายการชำระเงิน THE SYSTEM SHALL ตรึง `PspConnectionId`, `SecretVersionId` และ `PaymentEnvironment`
- 2.10 WHEN สภาพแวดล้อมหรือข้อมูลรับรองเปลี่ยน THE SYSTEM SHALL NOT เปลี่ยนค่าที่ตรึงไว้กับรายการชำระเงินเดิม
- 2.11 WHEN ผู้ดูแลระบบขอเปลี่ยนสภาพแวดล้อม THE SYSTEM SHALL เตรียมสภาพแวดล้อมใหม่พร้อมข้อมูลรับรองของผู้ให้บริการที่เชื่อมต่อทั้งหมด
- 2.12 WHEN มีคำขอเปลี่ยนสภาพแวดล้อม THE SYSTEM SHALL สร้างคำขออนุมัติแบบผู้ทำและผู้ตรวจ
- 2.13 IF ผู้ตรวจเป็นบุคคลเดียวกับผู้ทำคำขอเปลี่ยนสภาพแวดล้อม THEN THE SYSTEM SHALL ปฏิเสธการอนุมัติ
- 2.14 WHEN ผู้ตรวจอนุมัติการเปลี่ยนสภาพแวดล้อม THE SYSTEM SHALL เปิดใช้สภาพแวดล้อมและรุ่นข้อมูลรับรองใหม่ทั้งหมดภายในธุรกรรมเดียว
- 2.15 IF การเปิดใช้สภาพแวดล้อมหรือข้อมูลรับรองตัวใดล้มเหลว THEN THE SYSTEM SHALL คงสภาพแวดล้อมและรุ่นข้อมูลรับรองเดิมทั้งหมด
- 2.16 THE SYSTEM SHALL NOT อนุญาตให้การกำหนดค่าที่ใช้งานอยู่สำหรับรายการชำระเงินใหม่มีข้อมูลรับรอง sandbox และ live ปะปนกัน

## REQ-3: วงจรชีวิตของการเชื่อมต่อ

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการเชื่อมต่อ 2C2P และ Omise พร้อมกัน เพื่อให้ร้านค้าเลือกผู้ให้บริการที่เหมาะกับแต่ละช่องทางชำระเงินได้

**เกณฑ์การยอมรับ (EARS):**

- 3.1 THE SYSTEM SHALL อนุญาตการเชื่อมต่อหนึ่ง record ต่อ `(MerchantId, Psp)` สำหรับ `2c2p` และ `omise` โดยไม่ขึ้นกับสถานะเปิดใช้
- 3.2 THE SYSTEM SHALL อนุญาตให้ร้านค้าเดียวมีการเชื่อมต่อ 2C2P และ Omise พร้อมกัน
- 3.3 WHEN ผู้ดูแลระบบสร้างการเชื่อมต่อด้วยข้อมูลครบ THE SYSTEM SHALL กำหนด `IsEnabled=true` ทันทีโดยไม่บังคับทดสอบการเชื่อมต่อ
- 3.4 WHEN สร้างการเชื่อมต่อ THE SYSTEM SHALL กำหนดสถานะสุขภาพเป็น `unknown` จนกว่าจะมีผลทดสอบ
- 3.5 WHEN ผู้ดูแลระบบปิดการเชื่อมต่อ THE SYSTEM SHALL ไม่เลือกการเชื่อมต่อนั้นสำหรับรายการชำระเงินใหม่
- 3.6 WHEN ผู้ดูแลระบบเปิดการเชื่อมต่ออีกครั้ง THE SYSTEM SHALL ไม่บังคับให้การทดสอบผ่านก่อน
- 3.7 IF ร้านค้ามีการเชื่อมต่อของผู้ให้บริการเดียวกันอยู่แล้ว THEN THE SYSTEM SHALL ตอบ 409 โดยไม่สร้างซ้ำ
- 3.8 IF รหัสผู้ให้บริการไม่ใช่ `2c2p` หรือ `omise` THEN THE SYSTEM SHALL ตอบ 400
- 3.9 WHEN ผู้ดูแลระบบต้องการใช้การเชื่อมต่อเดิมที่ปิดอยู่ THE SYSTEM SHALL เปิด record เดิมกลับแทนการสร้าง record ใหม่
- 3.10 WHEN สร้างหรือเปิดการเชื่อมต่อ THE SYSTEM SHALL NOT เปลี่ยน routing ที่ใช้งานอยู่โดยอัตโนมัติ

## REQ-4: ข้อมูลรับรองและการกำหนดค่าเฉพาะผู้ให้บริการ

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลความปลอดภัย ฉันต้องการกรอกเฉพาะค่าที่ผู้ให้บริการต้องใช้และไม่สามารถอ่านข้อมูลลับกลับ เพื่อให้ลดความผิดพลาดและการรั่วไหลของข้อมูลรับรอง

**เกณฑ์การยอมรับ (EARS):**

- 4.1 WHERE ผู้ให้บริการเป็น 2C2P THE SYSTEM SHALL บังคับให้มี `merchantId` และ `secretKey`
- 4.2 WHERE ผู้ให้บริการเป็น Omise THE SYSTEM SHALL บังคับให้มี `secretKey`
- 4.3 WHERE ผู้ให้บริการเป็น Omise THE SYSTEM SHALL รับ `publicKey` และ `webhookSecret` เมื่อกระบวนการเชื่อมต่อต้องใช้
- 4.4 WHEN บันทึกข้อมูลรับรอง THE SYSTEM SHALL เก็บค่าที่อ่านได้เฉพาะในซองข้อมูลเข้ารหัสภายใน vault
- 4.5 WHEN API คืนข้อมูลการเชื่อมต่อ THE SYSTEM SHALL คืนเฉพาะส่วนท้ายที่ปกปิดต่อช่องข้อมูลลับ
- 4.6 THE SYSTEM SHALL NOT คืนข้อมูลรับรองที่อ่านได้หลังการตอบกลับการสร้างหรือการขอเปลี่ยนข้อมูลรับรอง
- 4.7 IF ช่องข้อมูลรับรองบังคับว่างหรือรูปแบบไม่ตรงกับผู้ให้บริการ THEN THE SYSTEM SHALL ตอบ 400 ก่อนเขียนข้อมูลลง vault
- 4.8 IF คำนำหน้ากุญแจ Omise ไม่ตรงกับสภาพแวดล้อมการชำระเงิน THEN THE SYSTEM SHALL ปฏิเสธก่อนเรียก Omise
- 4.9 THE SYSTEM SHALL แยกค่ากำหนดที่ไม่เป็นความลับออกจากซองข้อมูลรับรอง ยกเว้น `2c2p.merchantId` ที่อยู่ร่วมกับ `secretKey` ตามสัญญา vault เดิม
- 4.10 IF คำขอข้อมูลรับรองมีชื่อ field นอก allowlist ของผู้ให้บริการ THEN THE SYSTEM SHALL ตอบ 400
- 4.11 IF ค่าข้อมูลรับรอง field ใดเกิน 4,096 ตัวอักษร THEN THE SYSTEM SHALL ตอบ 400 ก่อนเขียน vault
- 4.12 IF request body สำหรับข้อมูลรับรองเกิน 16 KiB THEN THE SYSTEM SHALL ตอบ 413 ก่อนประมวลผล
- 4.13 WHEN API รับหรือบันทึกข้อมูลรับรอง THE SYSTEM SHALL ป้องกันการเก็บ response ใน cache ด้วย `Cache-Control: no-store`

## REQ-5: ความสามารถของช่องทางชำระเงิน

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการเปิดช่องทางชำระเงินแยกต่อผู้ให้บริการ เพื่อให้ร้านค้าควบคุมช่องทางรับเงินของแต่ละผู้ให้บริการได้

**เกณฑ์การยอมรับ (EARS):**

- 5.1 THE SYSTEM SHALL ใช้รหัสช่องทางชำระเงินมาตรฐาน `card`, `promptpay` และ `installment`
- 5.2 THE SYSTEM SHALL รองรับช่องทางชำระเงินทั้งสามแบบบนการเชื่อมต่อ 2C2P
- 5.3 THE SYSTEM SHALL แสดง `card`, `promptpay` และ `installment` ในหน้าตั้งค่าการเชื่อมต่อ Omise
- 5.4 WHEN ผู้ดูแลระบบเปิดช่องทางบนการเชื่อมต่อ THE SYSTEM SHALL ตรวจทะเบียนความสามารถของผู้ให้บริการและตัวเชื่อมต่อที่ลงทะเบียน
- 5.5 IF บัญชีผู้ให้บริการหรือตัวเชื่อมต่อที่ลงทะเบียนไม่รองรับช่องทาง THEN THE SYSTEM SHALL ปฏิเสธการเปิดช่องทางโดยปริยายแบบ fail-closed
- 5.6 WHEN ผู้ดูแลระบบปิดช่องทางบนการเชื่อมต่อ THE SYSTEM SHALL ไม่เลือกการเชื่อมต่อนั้นสำหรับช่องทางดังกล่าวในรายการชำระเงินใหม่
- 5.7 WHILE รายการชำระเงินถูกสร้างแล้ว THE SYSTEM SHALL คงช่องทางและผู้ให้บริการเดิมแม้ผู้ดูแลระบบแก้การตั้งค่าภายหลัง
- 5.8 THE SYSTEM SHALL NOT ใช้ CSV หรือ JSON ที่ไม่มีโครงสร้างข้อมูลตายตัวเป็นแหล่งตัดสินสิทธิ์ของช่องทางชำระเงิน
- 5.9 THE SYSTEM SHALL NOT รับ เก็บ ส่ง หรือสร้างโทเคนจาก PAN เพื่อรองรับช่องทางใด
- 5.10 THE SYSTEM SHALL NOT แสดง QR บนโดเมนแพลตฟอร์มเพื่อรองรับ PromptPay
- 5.11 IF ช่องทางของผู้ให้บริการยังไม่มีสัญญาการเปลี่ยนเส้นทางที่พิสูจน์ใน sandbox แล้ว THEN THE SYSTEM SHALL ถือว่าช่องทางนั้นยังใช้งานไม่ได้
- 5.12 WHEN ข้อกำหนดการเชื่อมต่อ Omise PromptPay หรือ installment ผ่าน sandbox และได้รับอนุมัติแล้ว THE SYSTEM SHALL อนุญาตให้เปิดช่องทางนั้น
- 5.13 THE SYSTEM SHALL ถือช่องทางระดับบัญชีผู้ให้บริการและนโยบายช่องทางระดับร้านค้าเป็นการตั้งค่าคนละระดับ
- 5.14 WHEN ผู้ดูแลระบบเปลี่ยนช่องทางระดับบัญชีผู้ให้บริการ THE SYSTEM SHALL NOT เปลี่ยนนโยบายช่องทางระดับร้านค้าโดยอัตโนมัติ
- 5.15 WHEN ระบบตัดสินช่องทางที่ใช้งานได้ THE SYSTEM SHALL บังคับให้ทั้งบัญชีผู้ให้บริการและนโยบายระดับร้านค้าเปิดอยู่
- 5.16 WHEN Admin Console แสดงช่องทางชำระเงิน THE SYSTEM SHALL แสดงสถานะระดับบัญชีผู้ให้บริการและระดับร้านค้าแยกกัน

## REQ-6: การกำหนดเส้นทางหลักและสำรอง

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการกำหนดผู้ให้บริการหลักและสำรองต่อช่องทางชำระเงิน เพื่อให้รายการชำระเงินใหม่เลือกผู้ให้บริการตามนโยบายร้านค้า

**เกณฑ์การยอมรับ (EARS):**

- 6.1 THE SYSTEM SHALL กำหนดการเชื่อมต่อหลักหนึ่งตัวต่อร้านค้าและช่องทางชำระเงินที่เปิดใช้
- 6.2 THE SYSTEM SHALL อนุญาตการเชื่อมต่อสำรองได้ไม่เกินหนึ่งตัวต่อร้านค้าและช่องทางชำระเงิน
- 6.3 THE SYSTEM SHALL อนุญาตให้ไม่มีการเชื่อมต่อสำรอง
- 6.4 IF การเชื่อมต่อหลักและสำรองเป็นตัวเดียวกัน THEN THE SYSTEM SHALL ปฏิเสธการกำหนดเส้นทาง
- 6.5 IF การเชื่อมต่ออยู่นอกร้านค้าเดียวกัน THEN THE SYSTEM SHALL ปฏิเสธการกำหนดเส้นทาง
- 6.6 IF การเชื่อมต่อไม่ได้เปิดช่องทางที่กำหนด THEN THE SYSTEM SHALL ปฏิเสธการกำหนดเส้นทาง
- 6.7 IF รุ่นข้อมูลรับรองที่ใช้งานอยู่ไม่ตรงกับสภาพแวดล้อมการชำระเงินของร้านค้า THEN THE SYSTEM SHALL ปฏิเสธการกำหนดเส้นทาง
- 6.8 WHEN สร้างรายการชำระเงิน THE SYSTEM SHALL เลือกการเชื่อมต่อหลักที่มีผลสำหรับช่องทางนั้น
- 6.9 IF การเชื่อมต่อหลักไม่ผ่านเงื่อนไขภายในก่อนส่งคำขอไปยังผู้ให้บริการ THEN THE SYSTEM SHALL เลือกการเชื่อมต่อสำรองที่มีผล
- 6.10 IF คำขอไปยังผู้ให้บริการหลักให้ผลกำกวมหรืออาจสร้างรายการภายนอกแล้ว THEN THE SYSTEM SHALL NOT สลับไปการเชื่อมต่อสำรอง
- 6.11 IF การเชื่อมต่อหลักใช้งานไม่ได้และไม่มีการเชื่อมต่อสำรองที่มีผล THEN THE SYSTEM SHALL ปฏิเสธก่อนสร้างรายการภายนอก
- 6.12 WHEN การกำหนดเส้นทางเปลี่ยน THE SYSTEM SHALL ใช้เส้นทางใหม่เฉพาะรายการชำระเงินที่สร้างหลังการเปิดใช้
- 6.13 WHEN มีคำขอเปิดใช้การกำหนดเส้นทาง THE SYSTEM SHALL ใช้การอนุมัติแบบผู้ทำและผู้ตรวจตามกลไกเดิมก่อนเปลี่ยนเส้นทางที่ใช้งานอยู่
- 6.14 THE SYSTEM SHALL กำหนดเงื่อนไขภายในของ routing จากสถานะเปิดใช้ ช่องทางที่รองรับ สภาพแวดล้อม และการมี reference ไปยังข้อมูลรับรอง
- 6.15 THE SYSTEM SHALL NOT ใช้ผลทดสอบสุขภาพเป็นเงื่อนไขตัดสิน routing
- 6.16 THE SYSTEM SHALL NOT เรียก PSP probe สดเพื่อเลือก routing ระหว่างสร้างรายการชำระเงิน
- 6.17 WHEN เปิดใช้ routing THE SYSTEM SHALL บังคับให้มีการเชื่อมต่อหลักครบทุกช่องทางระดับร้านค้าที่เปิดอยู่
- 6.18 IF ไม่มี active routing ที่ครอบช่องทางชำระเงิน THEN THE SYSTEM SHALL ปฏิเสธการสร้างรายการชำระเงินโดยไม่ใช้ค่าเริ่มต้นระดับ deployment
- 6.19 THE SYSTEM SHALL ให้หน้าตั้งค่าทั่วไปสร้างหรือแก้เฉพาะกฎต่อช่องทางที่ไม่มีเงื่อนไขยอดเงินและ Originator
- 6.20 IF active หรือ draft ruleset มีกฎตามยอดเงินหรือ Originator THEN THE SYSTEM SHALL แสดงกฎนั้นแบบอ่านอย่างเดียวและปฏิเสธการเขียนทับจากหน้าตั้งค่าทั่วไป
- 6.21 THE SYSTEM SHALL คง API และข้อมูล advanced routing เดิมไว้โดยไม่ลบหรือย้ายข้อมูลใน feature นี้

## REQ-7: การทดสอบการเชื่อมต่อและสถานะสุขภาพ

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการทดสอบข้อมูลรับรองโดยไม่สร้างรายการเงินจริง เพื่อให้ตรวจการเชื่อมต่อได้ก่อนหรือหลังเปิดใช้

**เกณฑ์การยอมรับ (EARS):**

- 7.1 WHEN ผู้ดูแลระบบสั่งทดสอบ THE SYSTEM SHALL เรียกคำขออ่านอย่างเดียวที่ยืนยันตัวตนกับผู้ให้บริการตามสภาพแวดล้อมของร้านค้า
- 7.2 THE SYSTEM SHALL NOT สร้างรายการเรียกเก็บเงิน การอนุมัติ หรือรายการชำระเงินระหว่างทดสอบการเชื่อมต่อ
- 7.3 WHEN การทดสอบสำเร็จ THE SYSTEM SHALL บันทึกสถานะสุขภาพ เวลาทดสอบ และผลลัพธ์ที่ตัดข้อมูลอ่อนไหวแล้ว
- 7.4 IF การทดสอบล้มเหลว THEN THE SYSTEM SHALL บันทึกสถานะสุขภาพเป็น `failed` และคืนข้อผิดพลาดที่ไม่เปิดเผยรายละเอียดภายใน
- 7.5 IF การทดสอบล้มเหลว THEN THE SYSTEM SHALL NOT ปิดการเชื่อมต่อโดยอัตโนมัติ
- 7.6 THE SYSTEM SHALL NOT บันทึกข้อมูลรับรอง ผลตอบกลับดิบของผู้ให้บริการ หรือตัวระบุอ่อนไหวในผลการทดสอบ
- 7.7 WHILE การทดสอบกำลังทำงาน THE SYSTEM SHALL ป้องกันผลลัพธ์เก่าเขียนทับรุ่นการเชื่อมต่อที่ใหม่กว่า
- 7.8 WHEN มีข้อมูลรับรองชุดใหม่รออนุมัติ THE SYSTEM SHALL อนุญาตให้ผู้มีสิทธิ์ทดสอบชุดใหม่นั้นแบบอ่านอย่างเดียวกับ endpoint ของสภาพแวดล้อมเป้าหมาย
- 7.9 WHEN ทดสอบข้อมูลรับรองที่รออนุมัติ THE SYSTEM SHALL แสดงผลที่ตัดข้อมูลอ่อนไหวแล้วแก่ผู้ตรวจ
- 7.10 WHEN ทดสอบข้อมูลรับรองที่รออนุมัติ THE SYSTEM SHALL NOT เปิดใช้ข้อมูลรับรองชุดนั้น
- 7.11 THE SYSTEM SHALL NOT บังคับให้ผลทดสอบข้อมูลรับรองที่รออนุมัติผ่านก่อนอนุมัติ

## REQ-8: การเปลี่ยนข้อมูลรับรองแบบผู้ทำและผู้ตรวจ

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลความปลอดภัย ฉันต้องการให้การเปลี่ยนข้อมูลรับรองผ่านผู้ทำและผู้ตรวจคนละคน เพื่อไม่ให้บุคคลเดียวเปิดใช้ข้อมูลลับใหม่ได้

**เกณฑ์การยอมรับ (EARS):**

- 8.1 WHEN ผู้ดูแลระบบขอเปลี่ยนข้อมูลรับรอง THE SYSTEM SHALL เตรียมรุ่นข้อมูลเข้ารหัสใหม่โดยไม่เปลี่ยนรุ่นที่ใช้งานอยู่
- 8.2 WHEN มีคำขอเปลี่ยนข้อมูลรับรอง THE SYSTEM SHALL สร้างคำขออนุมัติที่อ้างร้านค้า การเชื่อมต่อ ผู้ทำ และรุ่นข้อมูลใหม่
- 8.3 IF ผู้ตรวจเป็นบุคคลเดียวกับผู้ทำ THEN THE SYSTEM SHALL ปฏิเสธการอนุมัติ
- 8.4 WHEN ผู้ตรวจอนุมัติ THE SYSTEM SHALL เปิดใช้รุ่นข้อมูลใหม่ภายในธุรกรรมเดียว
- 8.5 WHEN ผู้ตรวจปฏิเสธ THE SYSTEM SHALL คงรุ่นข้อมูลรับรองเดิมที่ใช้งานอยู่
- 8.6 WHILE คำขอเปลี่ยนข้อมูลรับรองยังรออนุมัติ THE SYSTEM SHALL ใช้รุ่นข้อมูลรับรองเดิมกับรายการชำระเงินใหม่
- 8.7 IF การเชื่อมต่อมีคำขอเปลี่ยนข้อมูลรับรองที่รออยู่แล้ว THEN THE SYSTEM SHALL ปฏิเสธคำขอใหม่ด้วย 409
- 8.8 WHEN เปิดใช้รุ่นข้อมูลรับรองใหม่ THE SYSTEM SHALL บันทึกผู้ทำ ผู้ตรวจ เวลา และรหัสเชื่อมโยงโดยไม่บันทึกค่าที่อ่านได้
- 8.9 THE SYSTEM SHALL NOT มีจุดเชื่อมต่อ API สำหรับเปิดเผยข้อมูลรับรองที่บันทึกไว้ให้ผู้ดูแลระบบ

## REQ-9: ความปลอดภัยของ API และการแยกข้อมูลร้านค้า

**เรื่องราวผู้ใช้:** ในฐานะเจ้าของแพลตฟอร์ม ฉันต้องการให้การแก้ไขการตั้งค่าปลอดภัยต่อการลองซ้ำ การแก้ไขพร้อมกัน และขอบเขตร้านค้า เพื่อไม่ให้ข้อมูลซ้ำ ถูกเขียนทับ หรือรั่วข้ามร้านค้า

**เกณฑ์การยอมรับ (EARS):**

- 9.1 THE SYSTEM SHALL กำหนดขอบเขตข้อมูลการเชื่อมต่อ ช่องทาง เส้นทาง สภาพแวดล้อม และการอนุมัติด้วย `MerchantId`
- 9.2 THE SYSTEM SHALL ใช้ตัวกรองคำสั่งค้นหาตามร้านค้าและตัวป้องกันการเขียนแบบปิดตายกับเอนทิตีที่อยู่ในขอบเขตร้านค้า
- 9.3 WHEN API สร้างทรัพยากรหรือแก้ไขค่าที่อาจลองซ้ำ THE SYSTEM SHALL บังคับให้ส่ง `Idempotency-Key`
- 9.4 WHEN API แก้ทรัพยากรเดิม THE SYSTEM SHALL บังคับให้ส่ง `If-Match`
- 9.5 IF `If-Match` ไม่ตรงกับรุ่นปัจจุบัน THEN THE SYSTEM SHALL ตอบ 409 โดยไม่บันทึกข้อมูลบางส่วน
- 9.6 WHEN คำขอเดิมถูกส่งซ้ำด้วยกุญแจป้องกันการทำซ้ำและเจตนาเดิม THE SYSTEM SHALL คืนผลเดิมโดยไม่ทำงานซ้ำ
- 9.7 IF กุญแจป้องกันการทำซ้ำเดิมถูกใช้กับเจตนาต่างกัน THEN THE SYSTEM SHALL ตอบ 409
- 9.8 THE SYSTEM SHALL บังคับการป้องกัน CSRF กับจุดเชื่อมต่อ API สำหรับแก้ไขค่าของผู้ดูแลระบบทุกตัว
- 9.9 THE SYSTEM SHALL บันทึกประวัติแบบเพิ่มอย่างเดียวสำหรับการสร้าง เปิด ปิด เปลี่ยนช่องทาง ทดสอบ ขอเปลี่ยนเส้นทาง เปลี่ยนสภาพแวดล้อม และขอหรือตัดสินการเปลี่ยนข้อมูลรับรอง
- 9.10 THE SYSTEM SHALL NOT บันทึกข้อมูลลับที่อ่านได้ webhook ดิบ PAN หรือ authorization header ของผู้ให้บริการในบันทึกแอป บันทึกตรวจสอบ หรือผลลัพธ์การป้องกันงานซ้ำ
- 9.11 WHEN การทำงานอ่อนไหวสำเร็จ ล้มเหลว หรือถูกปฏิเสธ THE SYSTEM SHALL บันทึกผลลัพธ์ที่ตัดข้อมูลอ่อนไหวแล้วพร้อม actor และ correlation id

## REQ-10: การใช้งานผ่าน Admin Console

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการเห็นสถานะและตั้งค่าตามลำดับงานเดียว เพื่อให้เชื่อมร้านค้าได้ภายในเวลาที่กำหนดและไม่ตั้งเส้นทางผิด

**เกณฑ์การยอมรับ (EARS):**

- 10.1 WHEN ผู้ดูแลระบบเปิดหน้าตั้งค่าผู้ให้บริการรับชำระเงินของร้านค้า THE SYSTEM SHALL แสดงการ์ดผู้ให้บริการสำหรับ 2C2P และ Omise
- 10.2 WHEN ผู้ให้บริการยังไม่เชื่อมต่อ THE SYSTEM SHALL แสดงปุ่มสร้างการเชื่อมต่อ
- 10.3 WHEN ผู้ให้บริการเชื่อมต่อแล้ว THE SYSTEM SHALL แสดงสถานะเปิดใช้ สถานะสุขภาพ สภาพแวดล้อม เวลาทดสอบล่าสุด และส่วนท้ายข้อมูลลับที่ปกปิดแล้ว
- 10.4 WHEN ผู้ดูแลระบบเลือกผู้ให้บริการ THE SYSTEM SHALL แสดงเฉพาะช่องข้อมูลรับรองที่ผู้ให้บริการนั้นรองรับ
- 10.5 WHEN ผู้ดูแลระบบแก้ช่องทางชำระเงิน THE SYSTEM SHALL แสดงสถานะที่มีผลและเหตุผลเมื่อไม่สามารถเปิดช่องทางได้
- 10.6 WHEN ผู้ดูแลระบบตั้งเส้นทาง THE SYSTEM SHALL แสดงตัวเลือกหลักและสำรองต่อช่องทางชำระเงิน
- 10.7 IF ตัวเลือกสำรองไม่มีสิทธิ์ใช้งาน THEN THE SYSTEM SHALL ไม่ให้เลือกตัวเลือกนั้นและแสดงเหตุผล
- 10.8 WHEN แก้ไขค่าสำเร็จ THE SYSTEM SHALL โหลดมุมมองใหม่จากผลตอบกลับของเซิร์ฟเวอร์และ ETag ล่าสุด
- 10.9 IF การแก้ไขชนกับรุ่นที่ใหม่กว่า THEN THE SYSTEM SHALL โหลดสถานะปัจจุบันก่อนให้ผู้ดูแลระบบลองใหม่
- 10.10 WHILE คำขอเปลี่ยนข้อมูลรับรองรออนุมัติ THE SYSTEM SHALL แสดงสถานะรอโดยไม่แสดงข้อมูลลับชุดใหม่
- 10.11 THE SYSTEM SHALL รองรับการใช้งานด้วยแป้นพิมพ์และมีป้ายกำกับสำหรับเทคโนโลยีช่วยการเข้าถึงสำหรับช่องกรอก สถานะ และปุ่มทุกตัว
- 10.12 WHEN ทดสอบการใช้งานด้วยผู้ดูแลระบบใหม่ที่มีข้อมูลรับรองพร้อม THE SYSTEM SHALL ให้สร้างการเชื่อมต่อสองผู้ให้บริการ เปิดช่องทาง และส่งคำขอเปิดใช้ routing สำเร็จภายใน 5 นาทีโดยไม่ใช้คู่มือภายนอก

## REQ-11: ความพร้อมและความปลอดภัยของ webhook

**เรื่องราวผู้ใช้:** ในฐานะผู้ดูแลระบบส่วนกลาง ฉันต้องการเห็นและตรวจความพร้อมของ webhook ก่อนเปิดใช้จริง เพื่อไม่ให้ลูกค้าชำระสำเร็จแต่ระบบไม่รับผล

**เกณฑ์การยอมรับ (EARS):**

- 11.1 WHEN แสดงรายละเอียดการเชื่อมต่อ THE SYSTEM SHALL แสดง callback URL เฉพาะการเชื่อมต่อนั้นโดยไม่รวมข้อมูลลับ
- 11.2 WHEN ขอเปลี่ยนร้านค้าที่มี Omise connection ไปเป็น `live` THE SYSTEM SHALL บังคับให้ยืนยันว่า callback URL ถูกลงทะเบียนใน Omise Dashboard แล้ว
- 11.3 WHEN รับ webhook THE SYSTEM SHALL NOT เชื่อสถานะการชำระเงินจาก request body โดยตรง
- 11.4 WHEN รับ webhook ที่ผ่านขอบเขตตรวจสอบเบื้องต้น THE SYSTEM SHALL fetch-to-confirm สถานะกับผู้ให้บริการก่อนเปลี่ยนสถานะการชำระเงิน
- 11.5 WHERE ผู้ให้บริการมีลายเซ็นที่ตรวจสอบได้ THE SYSTEM SHALL ตรวจลายเซ็นก่อนประมวลผล webhook
- 11.6 IF ลายเซ็นที่ต้องตรวจไม่ถูกต้อง THEN THE SYSTEM SHALL ปฏิเสธ webhook โดยไม่ fetch-to-confirm
- 11.7 WHERE Omise ไม่มีสัญญาลายเซ็นที่ระบบตรวจสอบได้ THE SYSTEM SHALL ใช้ fetch-to-confirm ร่วมกับ rate limit และบันทึกข้อยกเว้นด้านความปลอดภัย
- 11.8 THE SYSTEM SHALL NOT เก็บหรือคืน webhook payload ดิบผ่าน Admin API

## กรณีขอบและประเด็นที่ต้องยืนยัน

- ตัวเชื่อมต่อ Omise ปัจจุบันรองรับ `card` เท่านั้น ส่วน PromptPay และ installment ต้องผ่านข้อกำหนดแยกและพิสูจน์ sandbox ก่อนเปิดความสามารถ
- Omise installment มีตัวเลือกธนาคารและระยะเวลาผ่อนเฉพาะผู้ให้บริการ การเลือกค่าดังกล่าวอยู่ในข้อกำหนดกระบวนการชำระเงินแยก
- สภาพแวดล้อมเป็นระดับร้านค้า และการเปลี่ยนสภาพแวดล้อมพร้อมข้อมูลรับรองต้องเปิดใช้พร้อมกันผ่านผู้ทำและผู้ตรวจ
- การเชื่อมต่อครั้งแรกมี `IsEnabled=true` ทันที แต่ไม่เปลี่ยน routing ที่ใช้งานอยู่
- การเชื่อมต่อสำรองใช้ได้เฉพาะเมื่อการเชื่อมต่อหลักไม่ผ่านเงื่อนไขภายในก่อนส่งคำขอไปยังผู้ให้บริการ
- ห้ามเปลี่ยนผู้ให้บริการหลังหมดเวลา ความผิดพลาดการรับส่งข้อมูล หรือผลกำกวมที่อาจสร้างรายการเรียกเก็บเงินแล้ว
- หน้าตั้งค่าทั่วไปใช้เส้นทางหลักและสำรองต่อช่องทาง โดยรักษากฎขั้นสูงเดิมแบบอ่านอย่างเดียว
