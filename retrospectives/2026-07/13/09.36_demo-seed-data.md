## Lessons Learned

- **Pattern**: noise ซ้ำ ๆ ใน tool output ที่ "ดูไม่มีพิษภัย" ต้องอธิบายให้ได้หนึ่งครั้ง ห้ามปัดทิ้ง — เคสจริง: `set -a && source .env` พ่น `command not found: User` ทุกครั้งตลอด session ผมประกาศว่า "harmless" แล้วเดินต่อ ที่จริงมันคือ zsh อ่าน `POL_DESIGN_SQL=Server=...;Database=...;User Id=sa;...` **ไม่ได้ quote** แล้วตีความ `;` เป็นตัวจบคำสั่ง -> ตัวแปรถูกตัดเหลือ `Server=localhost,11433` และ `User Id=sa` ถูกรันเป็นคำสั่ง. ค่าที่พังเงียบโผล่มาอีกที 5 ชั่วโมงถัดมาเป็น `pre-login handshake` error ของ `dotnet ef` ซึ่งดูไม่เกี่ยวกันเลย. — **Why**: "harmless noise" ที่ยังอธิบายไม่ได้ = สมมติฐาน ไม่ใช่ข้อสรุป; การปัดทิ้งทำให้ต้นเหตุถูกฝังไว้จนไป surface เป็นอาการที่ไล่ยากกว่ามาก. ต้นทุนของการเช็คหนึ่งครั้ง (~1 คำสั่ง) ต่ำกว่าต้นทุนของการไล่อาการปลายทางเสมอ.
- **Pattern**: ไฟล์ที่ gitignored (`.env`, `appsettings.Development.json`) เป็น **จุดบอดถาวรของ CI** — rename ที่ sweep ทั้ง repo แล้วเขียวหมด ยังทิ้ง key เก่าค้างในไฟล์เหล่านี้ของทุกเครื่องได้ และไม่มี gate ไหนจับ. เคสจริง: rf1 rename `ConnectionStrings:Producer` -> `App` แต่ `.env`/`appsettings.Development.json` บนเครื่อง dev ยังเป็น `Producer` -> `GetConnectionString("App")` ตกไปหยิบ `appsettings.json` ที่ commit ไว้ซึ่ง **password ว่างโดยตั้งใจ** -> `pol_app` ต่อ DB ไม่ได้ทั้งตัว แต่ boot ผ่าน (ไม่ fail-fast) เลยดูเหมือนปกติ. rename ที่แตะ configuration key ต้องมีรายการ "ไฟล์ local ที่ต้องแก้ด้วยมือ" ใน PR description + README เสมอ. — **Why**: sweep + CI เขียว ให้ความมั่นใจปลอมว่า rename จบแล้ว ทั้งที่ทุกเครื่อง dev พังเงียบ — และเพราะไฟล์ gitignored จึงไม่มีใครเห็นว่าเพื่อนร่วมทีมก็เจอเหมือนกัน.
- **Discovery**: `env -u FOO` ที่ **ไม่มีคำสั่งต่อท้าย** = `env` เปล่า = dump environment ทั้งก้อน (secret หลุดลง transcript). — **Why**: ผมพิมพ์ `env -u GH_TOKEN; sleep 60; gh pr checks` โดยเผลอใส่ `;` -> `GEMINI_API_KEY` จริงหลุด. `env -u VAR` ต้องตามด้วยคำสั่งเสมอ ไม่งั้นมันไม่ใช่ "unset แล้วรัน" แต่เป็น "print ทุกอย่าง". ขยายจากบทเรียนเดิมที่ครอบแค่ subagent — main thread ก็ทำหลุดได้ด้วย typo เดียว.
- **Pattern**: teammate 1 คน/task แบบ sequential + handoff ผ่าน `### Evidence` ใน `tasks.md` ได้ผลดีกับงานที่ task ต่อยอดไฟล์เดียวกันตามลำดับ FK — teammate คนหลังอ่าน Evidence ของคนก่อนแล้วไม่ต้องค้นซ้ำ และ **แต่ละคนเจอกับดักที่คนก่อนหน้าเจอไม่ได้** (T1 เจอ `QUOTED_IDENTIFIER`, T2 เจอ `MerchantCode` เก็บ lowercase, T5 เจอ `LINENO` เป็น reserved keyword). กุญแจคือให้ T1 วาง **โครงครบทุกตาราง** (DELETE block เต็ม) ตั้งแต่แรก แล้ว T2-T4 แค่เติม INSERT — ไม่มีใครต้องกลับไปแก้ของคนก่อน. — **Why**: fresh context ต่อคนทำให้ไม่มีใครแบก context หนักของทั้งฟีเจอร์ แต่ Evidence ที่บังคับให้เขียนทำให้ความรู้ไม่หายไปกับ context ที่ปิด.
- **Discovery**: verify step ของ task หนึ่งอาจ **พิสูจน์ไม่ได้จนกว่า task ถัดไปจะมีข้อมูล** — T1 ถูกสั่งให้พิสูจน์ REQ-2.4 (ลบก่อน stamp = PK collision) แต่ T1 ยังไม่มี INSERT ลงตาราง merchant-scoped เลย มันเลยพิสูจน์ตรง ๆ ไม่ได้ (comment step ออกแล้วสคริปต์ยัง exit 0). T1 รายงานตรง ๆ + ทำ standalone experiment แทน แล้วบอกว่า "ของจริงจะเห็นตอน T2" — T2 ได้ `Msg 2627 Violation of PRIMARY KEY constraint 'PK_Merchants'` จริง. — **Why**: agent ที่เจอ verify step ที่พิสูจน์ไม่ได้ มักจะแต่ง evidence ที่ "ผ่าน" แทนที่จะบอกว่าพิสูจน์ไม่ได้ — สั่งให้รายงานตรงเมื่อ verify ไม่ applicable ดีกว่าได้ evidence ปลอม.
