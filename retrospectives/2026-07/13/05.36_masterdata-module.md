## Lessons Learned

- **Pattern**: subagent verify step ต้องสั่งให้ **รัน gate จริงที่ CI รัน** (script ใน `docker/bootstrap/`,
  step ใน `.github/workflows/ci.yml`) ไม่ใช่ "query DB แล้ววาง output". เคสจริง: T2 verify การย้าย schema
  ด้วย SQL ที่มันแต่งเอง (ตาราง/grant/FK/seed ครบหมด เขียวสวย) แต่ `docker/bootstrap/assert-fresh-db.sql`
  ซึ่งเป็น required step ยังนับ `admin.Positions` อยู่ -> พังทุก fresh DB ด้วย `Invalid object name`.
  ผลพ่วง: ทุกครั้งที่ย้าย/rename ตาราง-schema ต้อง grep ชื่อ object เก่าใน `docker/` และ `.github/`
  ไม่ใช่แค่ `src/` + `tests/`. — **Why**: query ที่ agent เขียนเองย่อม pass เพราะมันเขียนตามสิ่งที่
  ตัวเองเพิ่งทำ — มันยืนยัน "โลกตรงกับที่ฉันคิด" ไม่ได้ยืนยัน "โลกตรงกับที่ระบบอื่นคาดหวัง"; คลาสเดียวกับ
  PR #79 (rf1) ที่ required check แดงเงียบมาตั้งแต่ commit แรก.
- **Pattern**: gate ที่ **skip แล้ว exit 0** = false green — เช็ค exit code อย่างเดียวไม่พอ ต้องอ่าน
  output ว่ามัน "ตรวจ" จริงหรือ "ข้าม". เคสจริง: `scripts/spec_trace.py` รับเฉพาะ heading `## REQ-N:` +
  เกณฑ์ `- N.M` + บรรทัด `Satisfies:` ใน tasks.md; requirements.md ที่ `/spec-quick` เขียนใช้
  `### REQ-N —` + `- **N.M**` -> script เข้า documented skip path, พิมพ์ข้อความข้าม, exit 0 ทั้งที่
  ไม่เคยตรวจอะไรเลย. — **Why**: spec-trace เป็น required CI check — false green แปลว่า spec drift
  ทั้ง spec ผ่านได้เงียบ ๆ; teammate T3 จับได้เพราะ*อ่าน* output ไม่ใช่เชื่อ exit code.
- **Discovery**: การย้าย entity ข้าม assembly ทำ **test ที่ถือ module/assembly list ของตัวเอง** drift
  เงียบ — `tests/Architecture.Tests/EntitySchemaMappingTests.cs` มี `ModuleAssemblies` hardcode ของมันเอง
  แยกจาก `HostModuleAssemblies.All` พอ EF config ของ Position/Office/Level/Division ย้ายออกจาก
  `Admins.Infrastructure` มันเลยเห็น schema เป็น null แล้วตกด่าน allowlist. — **Why**: ย้ายโมดูลครั้งหน้าให้
  grep หา list ของ assembly/module ทุกที่ (ไม่ใช่แค่ host wiring) ก่อนประกาศเสร็จ.
