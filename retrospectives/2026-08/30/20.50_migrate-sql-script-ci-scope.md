## Lessons Learned

- **Pattern**: `dotnet ef migrations script` ออก **1 batch ต่อ migration** แต่ `ef database update` รันทีละ command — raw `Sql()` ที่อ้าง column ซึ่ง `AddColumn` เพิ่งเพิ่มใน migration เดียวกันจะพัง `Invalid column name` ตอน compile batch ภายใต้ sqlcmd และผ่านหลอกถ้า DB มี column อยู่แล้ว (พิสูจน์แค่ migration ล่าสุดบน DB ที่ EF สร้างให้ 20/21 = เขียวปลอม) ต้องพิสูจน์จาก **DB ว่าง** เสมอ และแทรก `GO` ต่อ command (transaction ข้าม `GO` บน connection เดียวได้ abort กลางทาง rollback ครบ) — **Why**: false green จาก fixture ที่เตรียมสภาพให้ผ่าน; class เดียวกับ self-authored verification
- **Pattern**: guard ที่เขียนขึ้นเป็น **precondition ของงานเดียว** (`WHILE งานนี้ถูก implement` เช่น "SDD PR ห้ามแตะ product") ถ้าใส่ลง CI แบบรันทุก range จะกลายเป็นกฎถาวรที่ block งานปกติทั้ง repo โดยไม่มีใครเห็นจนกว่า PR ชนิดอื่นจะมา (PR #207 แตะแค่ `.githooks` เลยผ่าน, #208 เป็นตัวแรกที่แดง) ตอน cutover guard ต้องถามว่า "PR ชนิดที่ไม่ใช่งานนี้จะผ่านไหม" และ gate ด้วย scope ของ diff — **Why**: required check ที่แดงกับทุก product PR = repo ส่งงานไม่ได้ทั้งระบบ ต้องเปิด PR แก้ guard ก่อนงานจริง
- **Discovery**: `gh` token ที่มีแค่ `repo` push branch ที่แก้ `.github/workflows/*` ไม่ได้ (`refusing to allow an OAuth App to create or update workflow ... without workflow scope`) ต้องให้ user รัน `gh auth refresh -s workflow` เอง (เปลี่ยน auth = approval boundary) — **Why**: เจอตอน push ไม่ใช่ตอน commit ทำให้เสียรอบ ตรวจ `gh auth status` scope ก่อนเมื่อ PR แตะ workflow
- **Discovery**: `destructive-guard` บล็อก `DROP DATABASE` ผ่าน sqlcmd ทุกรูปแบบโดยไม่มี override; DB ทดสอบที่สร้างระหว่าง session ต้องให้ user ลบเองผ่าน `!` — **Why**: สร้าง DB ชั่วคราวให้น้อยและตั้งชื่อ prefix เดียวกันเพื่อให้คำสั่งลบสั้นและตรวจซ้ำง่าย
